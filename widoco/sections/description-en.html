bcfOWL: Description back to ToC

Composition over translation

bcfOWL follows one delegation rule. A BCF concept is delegated to an existing vocabulary if an established vocabulary covers its meaning without a shift. It stays in bcfOWL if no such vocabulary exists, or if BCF adds conditions that the other vocabulary does not express.

Delegated concepts

bcfOWL reuses the following vocabularies. It uses their terms by IRI and does not import them.

  • Dublin Core Terms (dcterms:): identity and creation
  • PROV-O (prov:): agents and change history
  • SOSA/SSN (sosa:): cameras and observations
  • SPOT (spot:) and GOM (gom:): spaces, poses, and transformation matrices
  • DCAT (dcat:): snapshot images and bitmaps
  • SKOS (skos:): extension values and schemes
  • BOT (bot:): building elements

The concepts are delegated as follows.

  • Identity and metadata (Dublin Core Terms, PROV-O): dcterms:identifier for BCF GUIDs, dcterms:creator and dcterms:created for creation. Authors, assignees, and project users are prov:Agents, so a person, an organization, or a software agent can take these roles.
  • Camera (SOSA): a camera is a sosa:Sensor, and a capture or a model view is a sosa:Observation. bcfOWL:hasPerspectiveCamera and bcfOWL:hasOrthogonalCamera point to the observation. The property tells the projection mode.
  • Pose (SPOT, GOM): the position and direction of a capture is a spot:PointSpace that represents the observation (spot:represents). It is placed in the building with SPOT appearances and a GOM transformation matrix.
  • Snapshot (DCAT, SOSA): the image is a dcat:Dataset with a distribution, and also the sosa:hasResult of the observation. bcfOWL:hasSnapshot refers to the same resource.
  • Building elements (BOT): a Component refers to a bot:Element with bcfOWL:hasElement.
  • Extensions (SKOS): the project-specific values for status, type, priority, label, and stage are skos:Concepts in one skos:ConceptScheme per category. A bcfOWL:ExtensionSchema refers to these schemes.
  • History (PROV-O): bcfOWL has no properties for change history. One possible pattern, with RDF 1.2 triple terms and PROV-O, is in the examples.

Format-specific core

The core contains the coordination concepts bcfOWL:Project, bcfOWL:Topic, bcfOWL:Comment, and bcfOWL:Viewpoint, and the visual state of a Viewpoint: selection, visibility and exceptions, components, coloring, lines, clipping planes, and bitmaps. The visual state contains instructions for a viewer, not statements about the building. bcfOWL therefore represents it directly, without more semantics.

Structural constraints

bcfOWL contains no cardinality restrictions. Under the open-world assumption, a missing title does not violate owl:minCardinality 1, and two status values are inferred to be the same individual. The BCF structure is a format requirement, not a statement about the world. It is therefore checked with the SHACL profile bcfOWL-shapes.

Examples

These Turtle files use the namespace https://example.org/bcfowl-example#. They build on each other.

  • 01-project.ttl: a Project, its users, and its extension schema.
  • 02-topic-comment.ttl: a clash Topic with a Comment.
  • 03-viewpoint.ttl: a Viewpoint with its camera, pose, and rendered image, and with selected components, coloring, a visibility exception, a clipping plane, a line, and an orthogonal plan view.
  • 04-provenance.ttl: the change history of a Topic with RDF 1.2 triple terms and PROV-O.
